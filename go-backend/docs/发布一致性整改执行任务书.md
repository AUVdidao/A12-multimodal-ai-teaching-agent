# LessonForge 发布一致性整改执行任务书

## 1. 整改 Goal

在发布负责人统一协调下，将 LessonForge 当前环境从 `NOT_READY` 推进到可重复验证的 `READY`；如果外部服务或产品决策无法满足，必须把状态保持为 `BLOCKED`，并明确阻塞证据，不能伪造完成。

整改必须形成闭环：

```text
现场基线 → 安全快照 → 版本/迁移对齐 → 服务恢复 → 生产入口核对
→ 真实 Generation 验证 → Artifact 完整性验证 → readiness 验收报告
```

## 2. 当前已知阻塞

- 磁盘源码已有 migration 011/012，运行镜像和数据库停在 010。
- 当前 `LESSONFORGE_ENABLE_GENERATION_WORKER=false`。
- PPT Engine、RAG/Backend API、Parser 当前未运行或不可达。
- 显式 Generation 入口已按产品规则实现，真实 Worker/Engine/Artifact 闭环仍未执行。
- `/healthz` 只有 liveness 语义。
- 历史 READY Artifact 中有物理文件缺失。

## 3. 执行原则

1. 先读后写：每个阶段先记录现场证据，再执行下一步。
2. 变更可回退：数据库写入前必须完成可验证的备份或快照。
3. 不删除数据：不得删除历史 Artifact、数据库行、volume、容器或镜像；异常记录先标记或隔离。
4. 不打印秘密：不得输出 API key、Bearer token、密码、加密密文或完整数据库连接串。
5. 单一变更负责人：同一时间只允许一个整改阶段修改运行环境，避免并发改变基线。
6. 不补造业务语义：ApproveDraft 是否自动创建 GenerationJob 未经产品确认前，不得擅自改变为自动生成；应先核对是否已有明确的显式生成入口。
7. 每阶段完成后必须向主任务汇报：实际动作、结果、证据、剩余阻塞和下一阶段建议。

## 4. 阶段计划

### 阶段 A：基线和安全快照

只读核对：

- 当前源码文件清单与 SHA-256 manifest
- Dockerfile、Compose、运行容器、镜像 digest
- 数据库 migration、关键表结构和历史 Artifact 统计
- 当前网络、volume 和外部服务状态

准备：

- 数据库备份或等价可验证快照
- 当前镜像、容器配置、Compose 展开配置的脱敏记录
- 不执行重启、migration、删除或 Artifact 修复

阶段输出：`baseline.md`、`version-matrix.md`、`backup-evidence.md`。

### 阶段 B：版本和数据库对齐

在阶段 A 快照成功后：

1. 从当前磁盘源码构建新的不可变镜像 tag，并记录 digest。
2. 只应用缺失的前向 migration 011/012；Generation 实现阶段另增加前向 migration 013；不得执行 reset、drop、truncate 或删除历史数据。
3. 查询并确认 `schema_migrations`、`model_connections` 和 `conversation_summaries` 与源码一致。
4. 重新启动或替换 server 前，先确认新镜像包含当前源码和 migration 文件。

如果备份失败、migration 非幂等或目标数据库不明确，立即停止并报告 `BLOCKED`。

### 阶段 C：运行依赖恢复

只使用现有 Compose/部署定义恢复 PPT Engine、RAG/Backend API、Parser；不得自行猜测新的镜像、网络或数据卷。

必须确认：

- 容器启动成功
- 同一网络可解析服务名
- 健康检查通过
- Engine 输入/输出共享卷与 Go backend 映射一致
- 不暴露秘密

如果外部栈的 Compose 定义缺失或启动会产生不明确的数据副作用，保持 `BLOCKED`，不要强行启动。

### 阶段 D：Generation 入口核对

只读定位：

- `LockedSpecification` 之后是否存在显式创建 GenerationJob 的 API 或服务
- 当前 HTTP 路由、Store 方法、数据库写入路径
- Generation Worker 是否只负责消费，还是同时负责创建

ApproveDraft 保持只创建不可变 LockedSpecification；产品确认后的显式入口、事务校验、活跃任务约束和前端状态闭环记录如下。

### 已冻结业务规则与实现范围（2026-09-11）

- `POST /api/missions/{id}/generation-jobs` 是教师在批准后单独点击“生成 PPT”触发的入口；请求必须携带精确 `specificationId` 与 `specificationVersion`。
- 入口事务校验 Mission 归属、精确规格版本、真实模板绑定、全部已绑定材料 `READY`，并写入 `QUEUED` GenerationJob 与 `GENERATION_REQUESTED` 活动；HTTP handler 不直接执行 SQL。
- 同一 Mission 同时最多一个 `QUEUED/RUNNING/VERIFYING` 任务；同一 LockedSpecification 的 `FAILED/CANCELLED/SUCCEEDED` 终态可再次请求，历史 Artifact 不删除。重复请求同一活跃规格返回已有 Job，不新增 Job。
- Worker 继续只消费已有 Job，状态沿用 `QUEUED → RUNNING → VERIFYING/SUCCEEDED/FAILED`；前端仅读取真实 Job/Artifact 状态，不伪造成功。

### 阶段 E：真实闭环验收

只有阶段 B/C 完成且 Generation 入口明确后才执行：

```text
已有 LockedSpecification
    → 显式创建 GenerationJob
    → Worker Claim
    → compose-plan
    → execute
    → 共享卷 PPTX
    → size/SHA-256 校验
    → Artifact READY
    → API 查询/下载
```

必须保留：Job ID、Artifact ID、脱敏请求链路、文件 size、SHA-256、HTTP 状态和时间戳。

### 阶段 F：就绪检查和最终报告

将 `/healthz` 与 readiness 语义分开，至少评估：

- HTTP 进程
- 数据库连接
- migration 版本
- Worker/队列
- shared storage
- PPT Engine、RAG、Parser

历史缺失 Artifact 不得直接删除；应形成异常清单和后续数据修复任务。

## 5. 完成标准

只有以下条件全部满足才报告 `READY`：

- 源码、镜像、数据库 migration 可追溯到同一发布基线
- 011/012/013 已安全落地并核对字段/表
- 外部服务可达且网络、共享卷一致
- GenerationJob 生产入口明确
- 完成一次真实 PPTX Generation 闭环
- Artifact 文件与数据库记录 size/SHA-256 一致
- readiness 能识别关键依赖故障
- 所有变更和回退证据已记录

否则报告 `NOT_READY` 或 `BLOCKED`，并列出下一步唯一阻塞项。
